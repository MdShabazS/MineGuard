## 1. Purpose, precedence and safety

This contract makes the agreed MineGuard sensing and evaluation behavior **precise, deterministic, testable and honest**. Red privately places synthetic hazard/decoy objects. Blue independently plans and flies a virtual drone. **Only the server** compares the drone's path and selected fictional sensor footprint against currently eligible objects and generates observations. Blue receives discovered **candidate observations only**, not the hidden scenario. At the legitimate mission end, an authorized results operation can compare candidates with historical private truth.

**This is not actual landmine detection.** Virtual surface, obscured and buried are categories in a simulated object model, not measured material properties. A simulated "buried" candidate does **not** show that an RGB, thermal, LiDAR or other real sensor detects underground ordnance. Advanced Mode probabilities are hand-configured synthetic behavior, not trained ML, experimental accuracy, or physical sensor specifications. No virtual survey establishes that real land is safe or "cleared." Optional real CV, if built later, must use harmless surrogate imagery and separate validation.

## 2. Definitions and fixed implementation coordinates

| Term | Contract meaning |
|---|---|
| **Hazard** | A private Red `ScenarioObject` with `kind='HAZARD'`, subtype `SURFACE`, `OBSCURED` or `BURIED` |
| **Decoy** | A private harmless Red `ScenarioObject` with `kind='DECOY'`, subtype `ROCK`, `SCRAP` or `CONTAINER` |
| **Candidate** | Server-emitted simulated observation; **not** a confirmed mine or proof of actual object type |
| **Active** | Object exists at this exact simulation event time, accounting for Live create/move/delete history |
| **Eligible scanned hazard** | Hazard active when it was first within the swept virtual sensor footprint |
| **Missed eligible hazard** | Eligible scanned hazard whose one deterministic Advanced trial produced no candidate |
| **Unscanned hazard** | Hazard never eligible for sensing during its active lifetime in the mission; **not** an FN |
| **False alarm** | Candidate generated by a decoy in Advanced; do not call it a real-world false-positive rate |
| **Sweep** | The union of circular ground-plane footprints along the actually traversed drone path |
| **Planned region** | Rectangle selected for grid mission (or explicit evaluation region), **not** proof of coverage |
| **Simulated time** | Server-owned mission time, increments only while RUNNING with speed multiplier |
| **Ground truth** | Private server-held object identities/types, positions and active time intervals; revealed only under explicit results authorization |

- The shared world ID is `mg-field-01`. X and Z each range **0 to 200 inclusive**, in fictional **virtual units**, not metres/GPS. Existing `worldToScene` offsets X/Z by 100; sensor computations **must use world X/Z**, not centered scene coordinates.
- Coordinates entered by Red follow `normalizeCoordinate` from `shared/scenario.ts`: finite, in bounds **before rounding**, then rounded to 0.1. Flight positions can have higher internal numerical precision than display.
- The drone's 3D Y/virtual altitude is visual and mission telemetry. For V0.1, detection is a **2D ground-plane proximity model**. Altitude does not secretly modify radius; do not imply a realistic camera projection or depth sensing.
- All hidden object categories are treated as fictional training labels. Trees/hills/roads are **visual scenery**, not physics-based occlusion; `OBSCURED` and `BURIED` effects are encoded only through the synthetic mode settings below.

## 3. One canonical virtual sensor configuration

**The numerical values below are newly selected V0.1 simulator constants** to make development and testing unambiguous; the earlier source documents approved profiles and qualitative behavior but did **not** fix actual radii or probabilities. They are not measurements or real hardware specifications.

### 3.1 Footprint profile radii (world X/Z ground plane)

| Profile | Radius `r` in virtual units | Full ground diameter `2r` | Suggested maximum gap-free grid lane spacing* |
|---|---:|---:|---:|
| `NARROW` | **6** | 12 | 12 |
| `STANDARD` | **10** | 20 | 20 |
| `WIDE` | **16** | 32 | 32 |

*Lane spacing `<= 2r` avoids gaps **between ideal infinite straight centerlines** in this fictional flat X/Z coverage model, assuming adjacent lines both run along the relevant region. It alone does **not** guarantee whole-rectangle coverage at borders/turns or real-world clearance. The actual swept route controls the covered area.

**Hard requirements:**
1. A single shared definition (e.g., `shared/sensor.ts`) must provide radii to backend sensing, route/profile UI, Three.js footprint overlay and report/results. No duplicate magic numbers. `STANDARD` is the default, independent of altitude.
2. A centered, visible circular footprint rendered above terrain represents a **fictional plan-view coverage radius**, not a real 3D camera cone. The visual circle/swept overlay must match precisely the backend `r` under all three camera modes and speeds.
3. Profile and `BASIC|ADVANCED` mode are chosen before Start and frozen in the mission's immutable configuration. UI can preview a changed profile only before flight; it cannot silently alter active mission detection rules.
4. Changing the visual camera, animation frame rate or window size cannot change sensor radius or which private objects become eligible.
5. All public labels say **Virtual footprint**, **Simulated sensor** or equivalent, and all distance/area units are clearly fictional.

### 3.2 Probability table for synthetic Advanced Mode

Use the first eligible exposure of each stable object ID in a mission. A single deterministic uniform random value `u` in `[0,1)` is compared with the configured threshold. Thresholds below are **project design constants**, not learned/verified probabilities.

| Active scanned object | Candidate emission threshold in `ADVANCED` | Synthetic interpretation |
|---|---:|---|
| `HAZARD/SURFACE` | **0.90** | 90% chance under the *simulation rule* |
| `HAZARD/OBSCURED` | **0.70** | 70% chance under the *simulation rule* |
| `HAZARD/BURIED` | **0.50** | 50% chance under the *simulation rule*, **not real subsurface sensing** |
| `DECOY/ROCK` | **0.20** | 20% synthetic false-alarm chance |
| `DECOY/SCRAP` | **0.20** | 20% synthetic false-alarm chance |
| `DECOY/CONTAINER` | **0.20** | 20% synthetic false-alarm chance |

- `BASIC`: **every** active in-footprint `HAZARD` is observed **exactly once**; decoys produce **no** candidates; no random miss or false alarm. Basic detecting a `BURIED` subtype is solely a synthetic rule.
- `ADVANCED`: on **first** eligible sweep encounter, perform exactly one deterministic seeded draw for that object. For a hazard, `u < p` generates a candidate; otherwise record private eligible-but-missed status. For a decoy, `u < 0.20` generates one **false-alarm candidate**; otherwise no public event.
- No extra ambient/background false positives are required for V0.1. This keeps every false alarm attributable privately to a specific scanned decoy for evaluation. Do not fabricate spontaneous coordinate pins.
- Do **not** roll every render frame or every tick: a single object's candidate/miss outcome is stable across speeds, pause/resume, reconnects and repeated passes in the same mission.
- Do not derive probability from altitude, camera angle, visual occlusion or perceived "AI confidence". No ML model has been trained.

## 4. Seeded randomness and repeatability

Use a **deterministic per-object draw** so reordering simultaneous object evaluations or changing the server tick frequency does not change outcomes. Suggested algorithm:

1. At mission creation freeze and persist `seed` (validated safe integer/string or cryptographically generated identifier), `sensorAlgorithmVersion='sim-v1'`, immutable `sensorMode` and `footprintProfile`.
2. Derive a reproducible number `u` from a well-documented stable hash/PRNG keyed by **mission seed + stable mission identity + stable scenario object ID + algorithm version** (e.g., SHA-256, then divide a fixed-width unsigned prefix by `2^53`). Keep canonical encoding and conversion constant across runs.
3. For a test/replay requiring identical outcomes, replay the **same persisted mission ID, seed and object IDs** and complete event sequence. Separate newly created rooms/objects naturally have different IDs; a common seed alone does not promise the same result across unrelated rooms.
4. Persist each object's first eligible decision (`DETECTED`, `MISSED`, `FALSE_ALARM`, `DECOY_IGNORED`) transactionally, so a restarted process can resume without reroll.
5. Never expose private object IDs, raw per-object random draws, hidden probability outcomes or unseen object counts to the Blue client. Public mode/profile/seed may be recorded in post-mission reporting; do not publish any table that indirectly reveals undiscovered placement identities during flight.

**Determinism means code/replay reproducibility, not a guarantee that a particular mission will have exactly 10%, 30% or 50% misses.** With small samples, realized frequencies can be very different.

## 5. Swept-segment geometry — no skipped hits at 4x

The authoritative server advances along **the actual traveled polyline**, with route legs possibly crossed within a single update at high playback speed. A client animation frame is not a scan event.

Given a traversed segment from `A=(ax,az)` at simulation time `tA` to `B=(bx,bz)` at `tB` and an active object's fixed position `P=(px,pz)`, compute point-to-segment proximity:

```text
D = B - A
s = clamp( dot(P-A,D) / dot(D,D), 0, 1 )  // use s=0 when D is zero
Q = A + s*D
distance = hypot(P.x-Q.x, P.z-Q.z)
eligible iff distance <= radius + epsilon
```

A preferable first-entry time calculation solves the earliest `s` on segment where `hypot(P-(A+sD)) <= radius`. For a stationary segment/starting inside the footprint, entry is at `tA`. For a normal segment, the earliest valid boundary intersection `sEnter` determines event time `tA + sEnter*(tB-tA)`. The nearest-point test may first discard out-of-range objects; **do not timestamp every detection at the segment endpoint** when it actually entered earlier. Use a small documented numeric tolerance for floating-point boundary cases, not a hidden enlarged footprint.

### Required chronological behavior

1. The flight engine yields **every** actually traversed subsegment, splitting any tick that passes one or more waypoints. Process them in increasing simulation time; no diagonal "shortcut" through a turn.
2. Evaluate private objects against the swept subsegment and their **active placement/movement intervals** at the correct event time, including Live changes that take effect partway through a tick. Split travel at any relevant committed mutation time, or maintain an equivalent precise ordered event timeline.
3. Only ACTIVE objects can become eligible. A hazard outside all swept footprints stays **unscanned and hidden**, regardless of its proximity to the starting plan rectangle or 3D camera view.
4. Objects at exactly the radius boundary count as scanned within numeric tolerance. An object just beyond radius stays unscanned; never reveal all nearby points from the server.
5. No duplicate event if a drone hovers, pauses, reverses, crosses the same point again or an object moves after its first decision; deduplicate on **(missionId, stableObjectId)** for the first eligible sensing decision. Store a stable private association.
6. If an object is first encountered later after being moved into the path, evaluate then; if it was already evaluated before moving, do **not** reroll or emit another candidate. Record subsequent exposure separately if useful, but the V0.1 score counts each object once per mission.
7. Pause freezes movement and simulation time. It must not trigger new sensing while stopped, nor accumulate repeated observations at the same coordinate.
8. STOPPED_EARLY finalizes **only the distance actually flown**, not the untraversed remainder. A planned route/rectangle is not equal to scanned coverage.
9. Sensor behavior must be invariant when repeating an identical route/mode/seed with 1x, 2x and 4x (subject to legitimate Live event-time differences). Speed affects completion time, not whether a static in-range object is eligible.
10. The private target coordinate and visible candidate X/Z may match exactly for V0.1; this is a fictional observation model without localization noise. The existence of a candidate is allowed to disclose **that candidate location only**.

**P0 versus later build:** MG-007 must preserve an ordered `previousPosition -> nextPosition` / `simTimeStart -> simTimeEnd` interface, including turns, for MG-008. MG-007 does **not** need to emit candidates or claim sensing works. Actual sweep geometry, dedup and candidates are MG-008.

## 6. Basic and Advanced event semantics

For each object with a **first eligible** encounter:
1. Lock or snapshot the object state/type and simulation event time, without exposing it publicly.
2. If Basic + Hazard: emit one candidate. Basic + Decoy: private `DECOY_IGNORED`, no event.
3. If Advanced + Hazard: deterministic roll for the subtype; either one candidate or a private `MISSED` evaluation.
4. If Advanced + Decoy: deterministic false-alarm roll; either one candidate or private ignored decoy.
5. Persist the private decision + candidate (if any) **before** broadcasting a public event. Reconnect/retry must not introduce a second candidate.
6. Emit to the correct room's **public** Blue subscribers only the safe candidate payload and public mission state; keep matched hidden object ID, private subtype, decoy classification and audit private.
7. Display a map pin and details panel for each **observed** candidate, not every eligible object. The same candidate ID appears in list, 3D marker and report.
8. No observation events for Advanced misses, ignored decoys or unscanned objects. No public "missed" counter before authorized finish.

### Observation model — suggested target

```ts
type CandidateReview = 'NEW' | 'REVIEWED';

interface PublicCandidate {
  candidateId: string;                   // server-generated ID, NOT the private object ID
  missionId: string;
  x: number; z: number;                  // observed fictional coordinates only
  simTimeSeconds: number;                // true first swept entry time
  source: 'SIMULATED';
  sensorMode: 'BASIC' | 'ADVANCED';
  footprintProfile: 'NARROW' | 'STANDARD' | 'WIDE';
  review: CandidateReview;               // optional user review, not truth verdict
}

interface PrivateSensorDecision {
  missionId: string;
  objectId: string;                      // private stable Red identifier
  activeObjectRevision: number;
  firstEligibleSimTime: number;
  outcome: 'DETECTED' | 'MISSED' | 'FALSE_ALARM' | 'DECOY_IGNORED';
  candidateId?: string;                  // if emitted
  scenarioRevisionAtEncounter: number;
}
```

Actual names can differ if Rahil updates [API_CONTRACT](../API_CONTRACT.md); role isolation and event meaning may **not** differ. Field `review` means a user clicked "reviewed" and must not alter server ground-truth TP/FP assignments.

## 7. Blue candidate map and detail panel

Blue's virtual survey view must display:
- Real-time **drone position**, planned route, actually flown path, and a translucent **current circular footprint** of the selected fictional radius. Camera and route view are defined by MG-005.
- **Automatically mapped candidate pins**, placed at the server-supplied public candidate X/Z only after an actual emitted observation. Nothing may leak before the drone approaches.
- A candidate list/panel with **candidate ID, fictional X/Z, simulated time, sensing mode, profile and review status**. Clicking a pin selects its card and vice versa. Show clear, projector-readable statuses.
- Candidate pins must be visually distinct from waypoints, drone, planned rectangle, observed/swept region and **post-finish revealed truth**.
- `No candidates yet` must be truthful. An Advanced miss or decoy ignored yields no pin.
- The UI may say **"Simulated candidate detected"**, not "Confirmed mine", "land cleared" or "AI classified buried mine".
- The current footprint circle and cumulative surveyed visual may be approximate on uneven terrain but must be faithful **in X/Z projection**. Do not recolor the entire planned rectangle as scanned at mission start.
- Keep observations stable across 2 tabs, refresh/rejoin and camera switching. A public list/API or snapshot supports recovery without duplicating pins.
- The map must show only actual results generated by the server. No hardcoded universal pins from ALPHA/BRAVO/CHARLIE fixture.
- Selection/review changes cannot edit private object data or cause new sensor trials.

## 8. Live Scenario changes, audit and non-retroactivity

The existing MG-004 `RoomStore` has scenario states (`DRAFT/LOCKED/RUNNING/PAUSED/FINISHED`), private mutation audit, `scenarioRevision`, and `setState` infrastructure. Integrate, do **not** bypass these.

| Live operation | Required sensing interpretation |
|---|---|
| CREATE during RUNNING | Object exists only from its **server-authoritative simulation timestamp** forward. If the drone already passed and never returns, it is **UNSCANNED**, not a missed in-range hazard. |
| MOVE during RUNNING | End old-position active interval, begin new-position interval at the mutation time. Past scan exposure is not recomputed. A never-before-eligible moved object can be scanned later. |
| DELETE during RUNNING | End active interval. No later exposure; existing historical detection/miss remains in audit/results. |
| CREATE/MOVE/DELETE during PAUSED | Apply at the current frozen simulated time, with deterministic order by server commit sequence; no simulated elapsed time passes and no retroactive event occurs. |
| Challenge LOCKED | Mutations remain server-rejected for the entire mission, including PAUSED; scanning cannot unlock. |
| FINISHED | Live edits disallowed until an explicitly new scenario/mission. Existing results frozen. |
| Multiple edits with equal simTime | Resolve in monotonic committed server event sequence, not in arbitrary websocket delivery order. |
| Two Red sessions editing concurrently | Respect MG-004 object revision conflict checking; a losing stale update must not influence sensing. |

**Important edge condition:** A static hazard becomes eligible only when active and in the actually swept footprint. A Live object that is created **inside the stationary paused drone footprint** must not be instantly detected merely because an edit occurred while the clock was frozen; evaluate at the first subsequent **RUNNING** simulation advancement (including zero/short motion) with the edited state. Document that consistent event-time rule and test it.

**First-exposure versus historical truth:** Maintain private per-object first eligibility and active time intervals. If a hazard was scanned and then deleted before finish, include it in the *historical scanned eligible set* (and count TP or FN according to the original outcome); don't erase it from truth just because it isn't active at end. Conversely, an object created too late or removed before ever entering a footprint is not an FN. If an object moves after a miss and is re-exposed, V0.1 does not retry (one decision per object per mission); this simplification must be disclosed in report limitations.

**No retroactive candidate:** Neither a Live mutation nor an end-of-mission truth reveal is permission to manufacture historical scan observations.

## 9. Persistence, synchronization and access boundaries

- Store private scenario changes, mission clock/segments, per-object eligibility decisions and candidates in server-side SQLite (or equivalent synchronized backend storage). **Do not store runtime records in GitHub**, browser local storage or a public world JSON.
- Write decision and observation atomically or use a transaction/outbox/idempotent publish strategy. A crash or duplicate Socket delivery cannot yield two distinct candidate IDs for one private object.
- Reconnect Blue: receive only safe mission snapshot and existing candidates; resumes from actual authoritative time/mission status and deduplicates by `candidateId` and monotonic event sequence. Do not replay hidden truth into browser memory.
- Red: may see its own private placements and optional authorized drone tracking (from public safe telemetry), but **private capability/token must never be sent to Blue** through observation routes, reports or logs.
- Room A's mission events, candidate IDs and list cannot leak into room B. Validate `roomCode` and `missionId` for every command/snapshot. No unrestricted global event broadcast.
- Public `GET /api/world` must remain a purely terrain endpoint; do not append private scenario data or seed-derived hidden object arrays.
- **Before authorized post-finish reveal:** public observation payloads must not contain private `objectId`, `kind`, `subtype`, `matchedObjectId`, `isFalseAlarm`, `wasMissed`, or any hidden noncandidate position. Internal database and Red-only snapshots may use those fields.
- A user with the public room code can act as a Defender, but cannot mutate Red ground truth, bypass Challenge lock or access private audit. Review of a public candidate is not a truth oracle.
- Source, type schemas, safe fictional fixtures and Rahil's sanitized QA evidence go to GitHub; raw attacker tokens, private active room URLs and runtime DB do not.

## 10. Coverage, truth reveal and metric definitions

**MG-008 owns the simulation and its events. MG-010 owns final evaluation UI/report/export, using the historical evidence generated by MG-008.** The present section specifies a shared evaluation contract so MG-007/008 cannot paint data they later cannot score.

### 10.1 Eligible, missed and unscanned truth sets

For a given `missionId`, define sets by unique private stable object ID and historical active interval:

- `H`: distinct hazard IDs that were **active at any point during the mission**.
- `E`: hazard IDs active when **at least one actual swept segment** came within configured radius, even if Advanced missed them; includes hazards later deleted.
- `D`: hazard IDs in `E` that produced a candidate (true observations).
- `M = E \\ D`: eligible scanned hazard IDs with **no candidate** (synthetic misses).
- `U = H \\ E`: hazards never scanned while active (unscanned/not exposed).
- `F`: **public candidate IDs** generated by decoys on eligible swept encounters, each mapped to private decoy ID internally.

Each unique hazard is counted once per mission. For a Live object with multiple active position intervals, eligibility is based on **at least one actual eligible interval**; do not compare only end-of-flight positions. Keep an explicit classification for objects removed before exposure if needed; they belong in `U` if they were active during this mission, not `M`.

`H` excludes hazards created only after the mission finishes; all counts/report denominators are tied to the mission's actual historical timeline.

### 10.2 Metric formulas

```text
TP = |D|                // observed unique eligible hazards
FN = |M|                // eligible scanned hazards with no candidate
FP = |F|                // candidate observations generated from decoys
UNSCANNED = |U|         // never eligible while active; NOT FN

precision = TP / (TP + FP), or N/A if TP+FP == 0
recall = TP / (TP + FN), or N/A if TP+FN == 0

eligibleScannedHazards = TP + FN
hazardsActiveDuringMission = TP + FN + UNSCANNED
```

- **No meaningless perfect score** when no hazards are eligible or no candidates exist: show **N/A**, not 100% or 0% by assumption for an undefined denominator. For an eligible hazard missed by Advanced, `TP=0,FN=1` => recall 0%, precision N/A if FP=0.
- Decoys ignored by Basic are **not false negatives**. An Advanced decoy yielding no observation is not a true positive or a false negative. True negative counts are not required.
- `REVIEWED` candidate status is a user workflow field, not a truth label; it must not change TP/FP/FN.
- A candidate event must have exactly one private source object, so matched `TP+FP` equals emitted unique candidate count. Do not compute precision from duplicate UI cards.
- Unscanned hazards are reported separately, even if they lie inside a *planned* rectangle that the flight stopped before reaching.
- For Live, make **time-dependent classification** visible in the final report (first eligible sim time, active change interval/revision). Do not grade against a static final snapshot.
- Report the scenario mode, virtual sensor mode/profile/radius, seed+algorithm version, completion reason (`ROUTE_COMPLETED` or `STOPPED_EARLY`), waypoint route, total actual distance and simulation time, number of hazards/decoys, and explicit **synthetic-only limitations**.
- Historical total counts and live object changes should be explained rather than blending objects that were never active during the mission.

### 10.3 Virtual coverage area — visually honest and bounded

Define a **swept region** as the union of circles of chosen radius centered along only the **actual traversed** polyline, clipped to world `[0,200]^2`. The planned grid rectangle is not equivalent to swept coverage.

For **grid routes**, `coveragePercent = 100 * area(swept region ∩ chosen rectangle) / area(chosen rectangle)`. For manual routes, show **actual swept virtual area**, and show a percentage only when a separate explicit evaluation region is defined (otherwise mark percentage N/A).

A lightweight deterministic **approximation** is acceptable for V0.1, e.g. a documented bounded fixed-resolution X/Z sample grid using cells and inclusion checks; report **"estimated virtual coverage"** and grid resolution. Clip to world/target area, count union only once, never multiply circles and double-count overlap. Avoid misleading exact precision such as 99.99999%. The method must work at borders and for short/early-stopped routes. A region with zero area is an invalid grid plan, not a divide-by-zero coverage value.

Coverage measures **where fictional sensing was applied**, not where hazards were confirmed absent, not GPS acreage, and not real clearance.
